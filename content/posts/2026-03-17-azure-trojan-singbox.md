  最近折腾了一次自建代理节点，目标很简单：

  - 服务器是一台 Azure 小规格 Linux 虚拟机
  - 系统是 Ubuntu 24.04.3
  - 客户端是电脑上的 Clash Verge 和手机上的 Clash Meta
  - 希望最终能在 Clash 里通过订阅方式导入使用

  最后方案跑通了，但中间踩了不少典型的坑。这篇文章把整个过程、原理和问题点整理一下，给自己留个复盘，也给同样想在小机器上自建的人参考。

  ## 为什么选这套方案

  一开始纠结过 Hysteria2 和 Trojan，最后选了：

  - 服务端：sing-box
  - 协议：Trojan
  - 客户端：Clash Verge / Clash Meta

  原因不复杂：

  - 小规格机器自用几个设备，跑 Trojan 完全够用
  - Trojan 对 Clash 兼容好，部署和维护成本低
  - sing-box 配置相对简单，资源占用也不高
  - 这个场景不是高并发，不需要为了“更强”去堆复杂协议

  所以目标就定成：用一个域名在 443 上跑基于 TLS 的 Trojan 节点。

  ## 第一坑：域名以为指过来了，其实没打到这台机器

  最开始我想直接用已有域名，结果一查发现不对：

  - 域名解析到的 IP 不是当前机器实际对外入口
  - 访问域名时返回的是另一台机器上的服务响应

  这说明“我以为 DNS 已经改好了”不等于“流量真的到了这台机器”。可能是：

  - 根域名本来就在另一台机器上
  - 看的“VPS IP”不是这台机器真正的入站公网 IP
  - 云厂商前面还有别的公网入口、NAT 或负载层

  后来改成一个新的子域名，并重新确认解析到当前机器的公网入口，问题才真正解决。

  这里学到的第一件事是：

  > 部署前先验证“域名是否真的打到当前机器”，不要凭感觉。

  ## 第二坑：DNS 对了，但 80/443 还是不通

  子域名解析正确之后，外部访问还是超时。

  这时候很容易误以为是 Ubuntu 配置有问题，但实际排查下来不是：

  - 本机 ufw 是关的
  - 本机没有奇怪的服务冲突
  - 外部访问的表现是“连不上”，而不是“连接被拒绝”

  这类现象通常说明问题在云厂商外层，不在系统内。

  最后确认是 Azure 那边的入站规则没放完整。对这个场景，至少要开：

  - 80/TCP 入站
  - 443/TCP 入站

  为什么两个都要？

  - 80/TCP 用来给 Let's Encrypt 做证书验证
  - 443/TCP 用来给 Trojan 节点本身使用

  为了确认流量到底能不能进机器，我还临时起了一个最简单的服务：

  sudo python3 -m http.server 80 --bind 0.0.0.0

  然后从外部访问域名。一旦能看到 Python 的目录页，就说明云上入口终于打通了。

  这个办法很土，但非常有效。

  ## 第三坑：证书申请成功了，但 sing-box 死活起不来

  后面安装了：

  - nginx
  - certbot
  - python3-certbot-nginx

  然后用 certbot --nginx 申请证书。

  证书是成功了，但 sing-box 启动后一直报错：

  listen tcp 0.0.0.0:443: bind: address already in use

  这类报错意思很明确：

  > 443 端口已经被别的进程占住了。

  一查果然是 nginx：

  sudo ss -ltnp | grep :443

  原因也很简单。certbot --nginx 不只是申请证书，它还会顺手改 nginx 配置并把 nginx 启起来，于是 443 就被 nginx 抢走了。

  但我的最终目标不是“网站跑在 nginx 上”，而是“让 sing-box 自己读证书并监听 443”。所以正确处理就是：

  sudo systemctl stop nginx
  sudo systemctl disable nginx
  sudo systemctl restart sing-box

  停掉 nginx 后，sing-box 就正常跑起来了。

  这一步的核心经验是：

  > 申请证书可以借助 nginx，但最终监听 443 的应该是你的代理服务本身。

  ## 第四坑：Clash 节点能用，但不是订阅链接

  节点跑起来后，最开始拿到的是这种东西：

  trojan://password@example.com:443?sni=example.com&security=tls#My-Node

  这个链接很多客户端能导入，但它本质上只是“单节点分享链接”，不是“订阅链接”。

  区别很重要：

  - trojan://... 是单个节点
  - http://.../clash.yaml 才是 Clash 订阅

  所以如果把 trojan://... 填到“订阅地址”输入框里，导不进去是正常的。

  后来我在服务器上额外做了一个极简静态文件服务：

  - 443 继续给 sing-box
  - 80 单独提供一个 clash.yaml

  这样就能像机场一样，在 Clash 里用订阅方式导入了。

  ## 第五坑：规则改了，但客户端更新后没变化

  一开始生成的 Clash 配置里只有这一条：

  rules:
    - MATCH,Proxy

  这等于几乎所有流量都走代理，相当于全局模式。

  后来我把规则改成了：

  rules:
    - GEOIP,LAN,DIRECT
    - GEOIP,CN,DIRECT
    - GEOSITE,CN,DIRECT
    - MATCH,Proxy

  意思就是：

  - 局域网直连
  - 中国 IP 直连
  - 中国站点直连
  - 其余走代理

  但改完以后客户端更新订阅，规则却没变。

  最后才发现原因不是客户端缓存，而是我改的是“源文件”，而订阅服务真正对外提供的是部署目录里的副本。

  也就是说：

  - 我改了 A 文件
  - 外部实际访问的是 B 文件

  当然不会变。

  把新配置同步到真正对外服务的那份文件后，问题才消失。

  这一步提醒我：

  > 静态订阅服务如果是复制部署，不是实时读取源文件，那后续更新必须同步到真正生效的那份文件。

  ## 第六坑：免密 sudo 明明写了，为什么就是不生效

  因为部署过程中很多地方都需要 sudo，每次输密码很烦，于是我给当前用户配了免密 sudo。

  内容本身没写错：

  username ALL=(ALL) NOPASSWD:ALL

  但是一直不生效。

  排查下来发现有两个问题。

  第一个问题是权限不对。/etc/sudoers.d/ 里的文件权限必须很严格，最开始那个文件不是 0440，所以 sudo 直接忽略它。

  第二个问题更隐蔽：即使权限修好了，后面加载的别的 sudo 规则还是把这条 NOPASSWD 给覆盖了。

  最后把文件改成一个字母序更靠后的名字，再配合正确权限，才终于生效。

  测试命令也很实用：

  sudo -n true && echo ok

  如果输出 ok，就说明免密 sudo 真的好了；如果还是提示需要密码，那就是没生效。

  ## 顺手解决的另一个问题：怎么看流量

  后面还装了 vnstat，用来看这台机器的网卡流量。

  安装方式很简单：

  sudo apt-get update
  sudo apt-get install -y vnstat
  sudo systemctl enable --now vnstat
  sudo vnstat -u -i eth0

  常用查看命令：

  vnstat -d
  vnstat -m
  vnstat -h

  这个工具的特点是：

  - 统计的是整张网卡的总流量
  - 不区分是不是 Clash、是不是某个客户端
  - 但对“专门跑代理的小机器”来说，已经足够接近真实使用量

  刚装完时它会显示：

  No data

  这不是故障，而是因为它不会回溯历史流量，只会从安装之后开始记。

  对自建用户来说，这个认知很重要：

  > Clash 客户端里看到的只是客户端自己的流量，不等于云厂商账单里的总出站流量。

  真正想看云平台会不会超免费额度，还是要结合：

  - 云平台控制台里的账单分析
  - 服务器侧的 vnstat

  一起看。

  ## GEOIP 和 GEOSITE 到底是什么

  后面配置分流时，用到了这几条规则：

  - GEOIP,LAN,DIRECT
  - GEOIP,CN,DIRECT
  - GEOSITE,CN,DIRECT
  - MATCH,Proxy

  它们的作用分别是：

  - GEOIP,LAN,DIRECT
    目标是局域网地址时直连，比如 192.168.x.x、10.x.x.x
  - GEOIP,CN,DIRECT
    目标 IP 如果属于中国大陆 IP 段，就直连
  - GEOSITE,CN,DIRECT
    目标域名如果属于中国站点集合，就直连
  - MATCH,Proxy
    前面都没命中，就走代理

  为什么要同时有 GEOIP 和 GEOSITE？

  - GEOIP 看的是最终解析出来的 IP
  - GEOSITE 看的是域名本身属于哪个规则集

  只用其中一个都不够，所以两者通常是配合使用的。

  ## 最后的成品结构

  最后这套东西的结构大概是这样：

  - 一个域名的 443 端口
    sing-box 提供 Trojan + TLS
  - 同一个域名的 80 端口
    一个极简静态文件服务，提供 Clash 订阅
  - Clash 客户端通过一个普通的订阅地址拉取配置
  - 规则采用基础分流：
      - 局域网直连
      - 中国流量直连
      - 其他走代理

  这套方案的优点是：

  - 成本低
  - 结构简单
  - 适合个人或少量设备自用
  - 对小规格机器很友好

  缺点也很明确：

  - 不是面板方案，没有漂亮的用户流量统计
  - 订阅只是静态文件，不带复杂功能
  - 证书续期和配置同步最好后续再自动化一下

  ## 这次最值得记住的经验

  这次部署最值得记住的，不是某一条命令，而是几个判断思路：

  - 域名是否真打到当前机器，要验证，不要猜
  - 外部“连不上”和“连接被拒绝”是两类完全不同的问题
  - 证书工具会顺手接管端口，别忘了回收
  - 订阅链接和节点链接不是一回事
  - sudoers 生效不只看内容，还要看权限和加载顺序
  - 客户端流量统计不等于云厂商账单流量

  如果以后我再从零部署一遍，这次踩过的坑基本都能提前避开。

  ## 结语

  这次折腾下来，一个很深的感受是：自建节点真正麻烦的地方，往往不是协议本身，而是部署链路里的各种小细节。

  协议选型、TLS、Clash 配置，这些都不算太难。真正容易卡住人的，反而是：

  - 域名是不是打到了正确机器
  - 云厂商入口有没有放通
  - 证书工具是不是抢了端口
  - 订阅到底是不是真的订阅
  - 规则到底有没有更新到实际生效的那份文件

  这些点每个都不复杂，但一旦叠在一起，就很容易把人绕晕。

  好在最后都跑通了，而且整个过程也顺便把常见坑都踩了一遍。以后再做类似部署，基本就有经验了。
